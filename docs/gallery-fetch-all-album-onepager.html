AGENT · GALLERY · SEARCH → ALBUM

「把所有猫猫照片建一个相册」：全量搜索如何接进现有 Skill 编排

搜索 Skill 目前按页返回（默认 500/页），2 万张要翻 40 次。要支持「全部 xxx 建相册」， 关键不是让谁去翻页，而是翻页在哪一层发生。结论：把「全量搜」做成搜索 Skill 的第二种 SOP，模型按意图选 SOP，相册 Skill 仍只消费结果引用； 不让模型循环翻页，不让相册 Skill 绕过搜索 Skill 去调不完整的 Tool，也不引入当前架构尚不支持的 Skill 调 Skill。

01

背景与约束

已支持：搜昨天的照片建相册 / 搜猫猫照片建相册（单页规格）

现状链路　模型调搜索 Skill → 结果写 workmemory（ID 列表 mask，summary 可见）→ 模型调创建相册 Skill，入参写 ${r1.merged_id_list} → Runtime 执行前回填真值。

新需求　「把所有猫猫的照片建成相册」——命中 2 万张，而搜索一次默认只回 500 张，现有链路只会把第一页塞进相册。

问题本质　「翻 40 页攒齐 ID」是一个循环，它必须落在某一层：模型、搜索 Skill、相册 Skill、Runtime。选错层，会带来 Token、时延、正确性或架构耦合的代价。

不可回避的两条　2 万个 ID 不该进模型上下文；相册写入若有单次上限，分批也不该由模型来做。

约束含义
搜索 Tool 不完整裸 Tool 缺搜索 Skill 里补齐的一截能力（排序 / 去重 / 语义改写 / 权限 / 摘要等），不能被其它 Skill 直接替代使用
暂不支持 Skill 调 Skill相册 Skill 执行层无法委托搜索 Skill 的 SOP；任何「相册内部去搜」都只能退化为调 Tool 或复制逻辑
已有引用机制workmemory + ${resultId.path} + mask + beforeHook，跨 Skill 传大列表是成熟路径
beforeHook 定位只做入参求值与结构转换（list → [{file_id}]），不是编排点
02

三个候选方案与各自的问题

差别只在「翻页循环」挂在谁下面
方案 A

模型自己翻页 不可取

search(query="猫猫", page=1)  → hasMore
search(query="猫猫", page=2)  → hasMore
… ×40
createAlbum(items=[${r1..r40} 拼接?])
  • 40 次 tool call，时延与 Token 不可接受，语音场景直接超时。
  • 模型要合并 40 个结果引用，现有 ${rN.path} 没有跨结果拼接语义。
  • 模型可能中途「觉得够了」提前停，相册漏图且无法察觉。
  • 把翻页这种确定性逻辑交给概率模型，是最贵也最不稳的一层。
方案 B（同事提议）

相册 Skill 内部直接调搜索 Tool 当前架构下不成立

createAlbum({ name:"猫猫", query:"猫猫" })
  └ 相册 Skill 执行层：
     loop searchTool(page++) 攒 ids
     createAlbumApi(ids)

本意是「一句话只调相册，翻页收进相册黑盒」，逻辑成立；但落地有三个硬伤：

  • 调的是不完整的 Tool：绕开搜索 Skill 补齐的能力，「猫猫」在两条路径下搜出的结果不一致。
  • 逻辑复制：想补齐就得在相册 Skill 里再抄一套搜索逻辑；拼图、发笔记若也要「全量」，各自再抄一份。
  • 职责倒置：相册 Skill 变成「搜 + 建」复合体，入参既收 items 又收 query，契约变胖，审计 / Gate / 失败归因都更绕。
  • 若改为「委托搜索 Skill 的 SOP」才能避免以上问题，但那就是 Skill 调 Skill，当前架构不支持。
方案 C（最终方案）

搜索 Skill 提供两种 SOP，模型按意图选 推荐

# 搜索 Skill
SOP default_search    # 现有：500/页，浏览挑图
SOP fetch_all_search  # 新增：Skill 内翻页攒齐

# 模型编排（不变的两步）
fetch_all_search(query="猫猫")      → r1
createAlbum(name="猫猫",
            items="${r1.merged_id_list}")
  • 翻页循环落在搜索 Skill 执行层，模型只发一次搜索、一次建相册。
  • 全量与默认是同一能力的两种规格，归属搜索 Skill 最自然；完整能力不被绕开。
  • 相册 Skill 零改动地继续消费引用；拼图 / 笔记 / 分享都能复用同一个全量结果。
  • 完全复用现有机制：workmemory、mask、${…} 回填、beforeHook 转结构。
03

最终方案的执行链路与配套规则

模型看 summary / total，ID 列表始终不进上下文

一次「全部猫猫建相册」的完整过程

STEP 1 · 模型选 fetch_all SOP（Skill 说明中约定：含「全部 / 所有 / 都 / 建相册 / 整理」走全量）
fetch_all_search({ "query": "猫猫" })
搜索 Skill 执行层（不经模型）：按 500/页翻页攒齐，可并行拉页；写入 workmemory r1
{
  "merged_id_list": [563, 728, … ]（20 000 项）,
  "total": 20000,
  "truncated": false,
  "summary": "找到约 2 万张猫猫照片"
}
送模后：merged_id_list → "${r1.merged_id_list}"  （mask）
         total / summary 可见
STEP 2 · 模型调相册 Skill，只写引用
createAlbum({ "name": "猫猫", "items": "${r1.merged_id_list}" })
Runtime 执行前：resolve → beforeHook 转结构 → 相册 Tool 内部按 API 上限分批写入
resolve → [563, 728, …]
transform → [{"file_id":"563"}, …]
createAlbumApi → batch(2000) × 10  对模型仍是一次调用

配套规则（落地 checklist）

层要做的事
搜索 Skill新增 fetch_all_search SOP：内部翻页、返回 total / truncated / summary；default_search 保持不变
Skill 说明写清路由：浏览 / 挑图 → default；全部 / 建相册 / 整理 → fetch_all；下游传参必须写 ${…merged_id_list}
Mask Policymerged_id_list 命中通用规则 mask；keep_visible: [summary, total]
相册 Skill只收 items 引用；beforeHook 负责 list → 对象数组；Tool 内部按 API 上限 batch
兜底策略超阈值（如 total > 5000）先向用户确认；硬上限时 truncated: true 写进 summary；拼图那套「截前 18」不复用到相册
语音体验fetch_all 耗时长：进度播报 / 可取消 / 超时降级为「先建前 N 张」

不做的事：不给相册 Skill 加 query 入参；不在相册执行层调搜索 Tool；不让模型循环 default 40 次伪装成全量。

04

为什么最终选 C

三个方案都能「拿到 2 万张」，差别在代价和边界
A · 模型翻页 B · 相册 Skill 内调搜索 Tool C · 搜索 Skill 双 SOP（最终）
tool call 次数 41 1 2（与现有链路一致）
翻页循环所在层 LLM 推理 loop 相册 Skill 执行层 搜索 Skill 执行层
搜索能力完整性 完整（走 Skill） 绕开 Skill，调不完整 Tool；或复制逻辑 完整，且默认 / 全量共用一套
依赖 Skill 调 Skill 否 想做对就需要（当前不支持） 否
职责边界 清晰但模型负担过重 相册 = 搜 + 建复合体，入参变胖 搜索管找，相册管建，Runtime 管传
结果复用 — 仅服务建相册 拼图 / 笔记 / 分享同样可接 ${r1…}
正确性风险 中途停、漏页、引用拼接错 两条路径搜索结果不一致 确定性循环 + fail-closed 回填
对现有机制的改动 无，但用错了 相册 Skill 大改 + 新增 Tool 依赖 搜索 Skill 加一个 SOP，其余零改动
主要残余风险 — — 模型偶发选错 SOP → 靠 Skill 说明 + 意图词路由收敛；B 的「一句话只调相册」可作为平台支持 Skill 调 Skill 后的增强
全量搜是搜索的规格　做成搜索 Skill 的第二种 SOP，不是相册的私有逻辑
翻页永远不进模型　循环在 Skill 执行层，模型只见 summary / total 和一个引用
相册只消费引用　沿用 workmemory + beforeHook，分批写入在 Tool 内完成
