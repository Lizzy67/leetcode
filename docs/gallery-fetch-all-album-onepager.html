「把所有猫猫照片建一个相册」：全量整理方案

搜索 Skill 一次 500 张，2 万张要 40 轮。核心问题是这 40 轮循环放在哪一层、靠什么保证不重、不漏、能停。最终方案以 SE 选型 2.1 为准：模型循环调用「搜索 → 追加」，靠搜索侧排除 + 相册侧追加去重保证幂等。

最终方案（SE 2.1）：模型循环「搜索 → 追加」，每轮 500 张搜索工具独立，引导模型引用搜索 / 新建相册 Skill

为什么模型循环这次能成立，以及必须钉死的点

成立的关键：每一轮都是幂等的 设计要点

search(…, exclude_album=X)不依赖 offset / cursor，永远返回「未入册」的前 500
↓
appendToAlbum(X, ids)追加去重，重放无副作用
↓ 重复直到本轮为空
  • 不重：搜索侧排除 + 追加侧去重，两层兜底。
  • 可续：任一轮失败 / 用户打断，下一轮从「还没进去的」继续，无需记页码。
  • 不重复建相册：首轮 create，之后只 append，albumId 走引用。
  • 与现有 workmemory / mask / ${…} 回填机制完全兼容。

残余风险与护栏 落地必须

  • 终止条件来自工具返回（remaining / hasMore / 本轮为空），不能只靠模型「感知未完成」；否则漏图或死循环都察觉不到。
  • 硬性 max_rounds + 可取消：2 万张 = 40 轮 LLM loop，时延与 Token 是主成本；语音侧需进度播报「已整理 3000 / 约 20000」。
  • ID 永不进上下文：每轮 500 个 id 仍 mask，模型只看 summary / remaining。
  • 排除条件的一致性：exclude_album 要以相册实时内容为准，避免追加尚未落库就发起下一轮导致重复命中。
  • 后续优化口：契约不变的前提下，可在搜索 Skill 内做 fetch_all 把 40 轮压回 1 轮（模型侧无感）。
