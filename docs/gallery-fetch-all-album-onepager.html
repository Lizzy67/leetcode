「把所有猫猫照片建一个相册」：全量整理方案

搜索 Skill 一次 500 张，2 万张要 40 轮。核心问题是这 40 轮循环放在哪一层、靠什么保证不重、不漏、能停。最终方案以 SE 选型 2.1 为准：模型循环调用「搜索 → 追加」，靠搜索侧排除 + 相册侧追加去重保证幂等。

裸循环翻页会撞上三件事：重复拉入 / 重复建相册 / 模型「觉得够了」提前停。方案 2.1 就是针对这三点补能力。

最终方案（SE 2.1）：模型循环「搜索 → 相册整理」，每轮 500 张搜索工具独立，引导模型引用搜索 / 新建相册 Skill；两个典型场景共用同一组原语

场景 1 · 一次指令，多轮接续找全（「目标对象」语义）　「帮我把猫咪的照片找到新建一个相册」
第 1 轮
search(query="猫咪", limit=500)
→
r1 · 500 ids（mask）· cursor · hasMore
→
createAlbum(name="猫咪精选", items=${r1.ids})
→
相册整理 Skill 判断本轮返回 = 500（或 hasMore）→ 未找全，回 need_more + next_cursor
→
TTS「正在查找照片，需要一些时间」
第 2…N 轮
search(query="猫咪", cursor=${r_prev.cursor})全量搜续页
→
rN · ≤500 ids · cursor
→
appendToAlbum(album=${r2.albumId}, items=${rN.ids})追加不新建；追加侧去重
→
整理 Skill 判断= 500 → need_more　< 500 → 结束
need_more → 模型自动再调一轮搜索 < 500 / hasMore=false → TTS「新增补充了 N 张照片」

循环的「继续 / 停止」由相册整理 Skill 的返回值触发，模型只是照着 need_more 再调一次搜索——判断在工具侧，不靠模型感觉。

场景 2 · 定期整理，新拍的移入已有相册（「增量」语义）　「把我上周新拍的猫咪照片整理到猫咪相册里」
首轮（早前）
search("猫咪")
→
createAlbum("猫咪精选")
→
相册【猫咪精选】已存在
追加指令
search(query="猫咪", time=上周, exclude_album="猫咪精选")【非】排除已在目标相册内的照片
→
r1 · 增量 ids
→
appendToAlbum(album="猫咪精选", items=${r1.ids})按名解析到已有相册，不重复新建
→
增量移入超 500 同样走场景 1 的 cursor 循环
搜索 Skill 扩展
分页参数（limit / cursor，返回 hasMore）；【非】排除逻辑（exclude_album）；多轮整理 / 分页的能力说明。
新建相册 Skill 扩展
首轮新建、后续按名 / id 追加不重复新建；追加去重；返回 need_more / next_cursor 驱动下一轮；每轮上限 500。
模型层 & 播报
引用 ${r.albumId} / ${r.cursor} / ${r.ids}；见 need_more 即再调搜索。工具说明 + 基模输出友好提示：「正在查找照片，需要一些时间」「新增补充了一些照片」。

为什么模型循环这次能成立，以及必须钉死的点

成立的关键：两个原语 + 一个机械判断 设计要点

search(query, cursor | exclude_album)场景 1 用 cursor 续页；场景 2 用排除做增量；可叠加
↓
album(create | append, dedup)首轮 create，之后 append；追加去重，重放无副作用
↓
整理 Skill 返回 need_more本轮 = 500 → 继续；< 500 → 停
  • 不重：搜索侧排除 + 追加侧去重，两层兜底。
  • 不漏 / 能停：继续与否由整理 Skill 按「返回条数」机械判定，不是模型感觉。
  • 不重复建相册：首轮 create，之后按名 / id append。
  • 不需要 Skill 调 Skill：整理 Skill 只是「回一个 need_more」，真正再调搜索的仍是模型。

残余风险与护栏 落地必须

  • 「= 500 继续 / < 500 停」要写对方向，并优先用搜索返回的 hasMore 兜底：恰好命中 500 的整数倍时，仅靠条数会多跑一轮空搜索（可接受），但方向写反会只整理一页。
  • 终止条件来自工具返回（need_more / hasMore），不能只靠模型「感知未完成」；否则漏图或死循环都察觉不到。
  • 硬性 max_rounds + 可取消：2 万张 = 40 轮 LLM loop，时延与 Token 是主成本；语音侧需进度播报「已整理 3000 / 约 20000」。
  • ID 永不进上下文：每轮 500 个 id 仍 mask，模型只看 summary / remaining。
  • cursor 与排除的一致性：cursor 需在多轮间稳定（新拍照片插入不应打乱续页）；exclude_album 要以相册实时内容为准，避免追加未落库就发起下一轮。
  • 后续优化口：契约不变的前提下，可在搜索 Skill 内做 fetch_all 把 40 轮压回 1 轮（模型侧无感）。
