AGENT · TOOL CALLING

工具参数引用：让模型写「引用」，让 Runtime 填「真值」

工具入参不再由模型亲手写出真实值，而是写一个引用；Runtime 在工具执行前查表求值、按需转换、校验合法，再去调用工具。 真值始终出自可信数据源，存量工具一行不改。

01

为什么要做

串行工具链里，下一个工具的参数常常来自上一个工具的结果，或者来自「抖音」这类口语名称背后的真实标识。 这些值现在都靠模型亲手写：长 URI 抄着抄着就断了；包名靠记忆，就编出了 com.douyin.app； 上下游结构不一致时，还要模型手工改写大段 JSON。抄写、回忆、改写——三件事模型都做不稳。

抄不准：长值复述易截断改写，还抬高输入 Token 会编造：弱语义标识凭记忆幻觉 改不动：结构适配靠模型或逐个改工具，都不划算
02

方案主链路

Reference → Resolve → Invoke，全部发生在工具执行之前
工具 A
结果入库
返回结果写入工作记忆，得到短标识 resultId
Runtime
送模呈现
指针字段直接换成引用给模型看；要推理的内容照常给
模型
只写引用
下游参数填 ${…}，不复述真值，所见即所填
Runtime
求值 · 转换 · 校验
查表回填真值，按参数策略适配结构，验完 Schema 与权限
工具 B
真值执行
校验通过才调用；结果再入库，链路闭环
03

三个关键问题

引用怎么写

上一步的结果，用 ${resultId.path} 指定字段；「抖音的包名」这类稳定标识， 写成 ${app.抖音.bundleName}。两种写法走同一条解析管道。

模型不需要看值时，送模前就把值换成引用，模型照抄即可；需要看值推理时，内容照常给， 但参数里仍然写引用——「看」与「传」分开。

真值从哪来

结果引用查工作记忆：先查全量结果集，再查工具适配视图。 语义引用查词典：先把 douyin、Douyin 归一成「抖音」，再由映射表给出真实包名。

结构不一致时按参数策略转换：[563,728] 自动变成 [{"file_id":"563"},…]，模型和工具都不用动。

出错怎么办

解析失败、映射歧义、转换出错，一律短路：${…} 原文绝不透传给工具， 错误明确回给模型。权限与作用域由 Runtime 校验，模型说了不算。

语义映射没命中，就退回查询工具拿候选，确认后刷新词典再重试—— 失败只是多一轮，不会错着执行。

省 Token长值不再回灌复述，输入与时延同降
消幻觉标识只出自查表，不靠模型记忆
少一轮映射命中时，一次业务调用完成
零改动能力在框架层，存量工具无感接入

模型决定引用哪个对象，Runtime 保证真实、适配、合法，然后才执行。
