智能体工具参数引用方案

模型表达“引用谁” · Runtime负责“取真值、做转换、再调用” · 工具零改动
结果引用 ${resultId.path}　语义引用 ${namespace.entity.attribute}

为什么需要

  • 长URI/列表让模型照抄：Token高、易截断改写
  • 包名等弱语义标识：模型易凭记忆编造
  • 上下游Schema不同：让模型改长JSON不稳定

核心原则

  • 模型只输出引用意图，业务真值来自工作记忆/语义词典
  • 统一Pre-call流水线：求值 → 可选转换 → 校验 → 调工具
  • 工具无感知：存量工具仍接收原有真实参数

可靠性底线

  • 解析/映射/转换/Schema任一失败即短路
  • 禁止把${…}字面量或半成品透传工具
  • 权限与作用域由Runtime校验，模型不能决定

完整主链路

① 工具返回工具A产出URI、ID、列表或对象
② 默认入库写入工作记忆并生成resultId
③ 送模按需mask；或保留内容+引用
④ 模型填引用下游参数写引用，不复述真值
⑤ 引用求值查工作记忆或语义词典回填
⑥ 转换/校验按Policy适配结构并校验Schema
⑦ 执行闭环真值调用工具B；结果再次入库

两类引用 · 同一管道

A工具结果引用

${a1b2c3d4.fileUri} → Workmemory

B语义实体引用

${app.抖音.bundleName} → 别名归一 + 属性映射

两种可见性

  • 模型不用看值：送模前mask为引用，所见即所填
  • 模型需要看值：内容/摘要供推理，工具入参仍写引用
约束层级：Runtime硬校验 ＞ Schema/Skill ＞ SystemPrompt

引用后可做结构适配

模型：images=${rid.merged_id_list}
Resolve：[563, 728]
Transform：[{"file_id":"563"},{"file_id":"728"}]
先求值，再按目标工具参数Policy转换；模型和工具均不用改结构。

关键实现约定

  • 结果默认写入Workmemory；查询可兼容全量结果集 → 工具适配视图
  • resultId为模型侧短标识；内部toolCallId继续用于追踪
  • 通用mask字段（fileUri/fileId等）支持工具级覆盖

核心收益

  • 降Input Token与串行时延
  • 减少长值抄错和业务标识幻觉
  • 热路径少一次查询Loop
  • 框架统一接入，工具零改动

边界与兜底

  • 多候选不静默猜：返回候选/动态枚举
  • 未命中可调用查询工具，确认后刷新映射
  • 并行链路必须显式引用，不用含糊“上一条”
一句话：模型只决定“引用哪个对象/结果”，Runtime保证“真实、适配、合法”后再执行。 Reference → Resolve → Transform → Validate → Invoke
