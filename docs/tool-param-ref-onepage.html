智能体工具参数引用方案

结果引用 ${resultId.path}　语义引用 ${namespace.entity.attribute}

问题：模型直接生成业务真值不可靠

抄不准
长URI/列表照抄易截断改写，Token高
会编造
包名等弱语义标识凭记忆幻觉
改不动
上下游Schema不同，改长JSON不稳、改工具成本高
→

核心思路：职责分离

模型只表达“引用谁”，Runtime负责“取真值、做适配、保合法”
  • 真值只来自可信数据源（工作记忆 / 语义词典）
  • 全部处理收敛在工具执行前的统一入口，工具零改动

主链路：Reference → Resolve → Invoke

Ⅰ 引用表达（模型侧）
① 结果入库工具A返回，写入工作记忆并生成resultId
② 送模呈现指针字段mask成引用；要推理的保留内容+引用
Ⅱ 求值与适配（Runtime侧）
③ 模型填引用下游入参写${…}，不复述真值
④ 引用求值查工作记忆 / 语义词典，回填真值
Ⅲ 校验与执行（工具侧）
⑤ 结构适配按参数Policy做转换（可选）
⑥ 校验/短路Schema与权限校验；失败不透传
⑦ 执行闭环真值调工具B；结果再入库

支柱Ⅰ：引用怎么写

两类引用，同一管道
  • 结果引用 ${a1b2c3d4.fileUri} → 工作记忆
  • 语义引用 ${app.抖音.bundleName} → 词典
两种可见性
  • 不用看值：mask后所见即所填
  • 需要看值：内容供推理，入参仍写引用

支柱Ⅱ：真值怎么来

可信数据源
  • 工作记忆：全量结果集 → 工具适配视图
  • 语义词典：别名归一表 + 实体属性映射表
结构适配（Policy）
${rid.merged_id_list} → [563,728] → [{"file_id":"563"},…]

支柱Ⅲ：错误怎么兜

硬约束（Runtime）
  • 解析/映射/转换/Schema失败即短路，禁止${…}透传
  • 作用域与权限由Runtime校验，模型无权决定
可恢复（兜底）
  • 多候选返回列表/动态枚举，不静默猜
  • 未命中→查询工具→确认后刷新映射→重试
省Token长值不回灌不复述，降输入与时延
消幻觉真值只出自查表，标识不再编造
少一轮映射命中时业务调用1次Loop完成
零改动框架层统一生效，存量工具无感
一句话：模型决定“引用哪个对象”，Runtime保证“真实、适配、合法”后再执行。
