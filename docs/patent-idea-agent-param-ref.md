## 一、背景技术

### 1.1 应用场景

在基于大语言模型的智能体系统中，模型通过 Function Calling / Tool Calling 选择并调用外部工具。典型链路为：

用户意图 → 模型决策并发起工具调用（携带参数）→ 运行时执行工具 → 结果回灌模型 → 模型再决策 / 再调用。

该链路在以下场景尤为常见：

1. **跨工具传参**：上一工具返回文件地址、对象标识、大段文本等，下一工具需要同一字段作为入参。  
2. **语义弱的业务标识入参**：例如操控手机应用时，工具要求填写应用包名（bundleName / packageName）。包名命名不规范、语义性弱，用户口语常为「抖音」「微信」等应用名。  
3. **跨工具传参且结构需转换**：上一工具返回标识列表等结构，下一工具要求对象列表（如每项含 `file_id`）。若由模型改写结构，列表稍长即易错；需要在引用展开后由运行时按策略自动做格式转换。

### 1.2 现有做法及缺陷

**业界常见做法包括：**

- 将工具完整返回结果再次输入模型，由模型在下一轮工具参数中**原样填写**所需字段；  
- 对包名等标识，要求模型先调用「查询已安装应用列表」类工具，再根据列表结果填写真实包名后调用业务工具（**两次循环**）；  
- 或依赖提示词要求模型“不要编造”，但仍由模型直接输出疑似真实的包名 / URI 字符串；  
- 部分系统在提示词模板或工作流脚本中做变量替换，但替换对象通常是**编排脚本预置变量**，而非模型在工具入参中主动输出的统一引用协议；另有方案侧重密钥等机密注入，将参数从模型可见 schema 中剥离，由运行时注入，模型不表达业务引用意图。

**上述做法存在的问题：**

| 问题 | 说明 |
|------|------|
| A. 多轮开销 | 为拿到真实标识常需额外查询轮次（如先查已安装列表再调业务工具）。 |
| B. 幻觉风险 | 包名等弱语义标识易被模型凭记忆编造（如错误包名），导致工具调用失败或误操作。 |
| C. 照抄错误 | 长 URI / 大字段 / 长列表要求模型复述或改写结构时易截断、改写，遵从性差，且抬高 Input Token。 |
| D. 结构不匹配 | 上游列表与下游对象数组等 schema 不一致时，缺统一的执行前转换，只能改工具或让模型变形。 |
| E. 工具难改造 | 带 bundleName、fileUri 等参数的工具数量多，无法逐个改造工具实现或签名。 |
| F. 真值权威在模型 | 现有链路中“填什么字符串”最终仍由模型生成，缺乏“真实值只能来自查表/记忆”的结构性约束。 |

**故现有技术难以同时满足：** 正常路径少轮次完成调用、工具零改动全覆盖、真实标识不由模型编造、上下游结构解耦。

## 二、技术方案

### 2.1 发明点定位

本发明属于对现有「模型直接生成工具入参真值」流程的改进：在工具调度框架中增加**统一的参数引用协议**与**调用前解析拦截**，使模型只输出引用意图，真值由框架在执行前查表求值。

### 2.2 总体架构（建议附图：原理框图）

```
┌────────────┐   工具调用请求(含 ${…})    ┌──────────────────────┐
│  大模型     │ ───────────────────────► │ 工具调度 / 编排层      │
└────────────┘                           │  + 引用解析拦截器      │
                                         └──────────┬───────────┘
                                                    │ 求值
                          ┌─────────────────────────┼─────────────────────────┐
                          ▼                         ▼                         ▼
                 ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
                 │ 工作记忆         │      │ 语义词典         │      │ 短句柄映射(可选)  │
                 │ 工具结果集合     │      │ 同义词表+映射表   │      └─────────────────┘
                 └─────────────────┘      └─────────────────┘
                                                    │
                                                    ▼ 回填真值后
                                         ┌──────────────────────┐
                                         │ 工具执行模块（无改动） │
                                         └──────────────────────┘
```

**改进点在整体流程中的位置：** 位于「模型已产出 tool call」与「工具真正执行」之间；工具实现与参数签名保持不变。

### 2.3 核心流程（建议附图：时序图 / 流程图）

**步骤 S1：结果默认入库（针对跨工具传参）**  
工具执行成功后，编排层将返回结果写入会话工作记忆，分配模型侧短结果标识 `resultId`，并保存与内部调用标识的映射。

**步骤 S2：送模前可选掩码**  
按「通用字段规则 + 单工具覆盖规则」决定字段可见性。对文件地址、文件标识等指针型字段，可将真值替换为引用占位符后再送入模型，使模型感知变量但不必阅读/抄写长串。

**步骤 S3：模型输出带占位符的工具入参**  
模型在需要真实标识或上游结果字段处，填写统一形态的引用占位符（见 2.4），禁止编造真实包名 / 长 URI。

**步骤 S4：调用前拦截与解析（关键改进点）**  
在所有工具 invoke/exec 的统一入口：

1. 扫描参数叶子节点字符串，识别形如 `${…}` 的占位符；  
2. 按规则判别引用类型并求值（见 2.4、2.5）；  
3. 求值成功则替换为真值后调用工具；  
4. 求值失败则**短路**，返回明确错误，**禁止**将 `${…}` 字面量透传给工具。

**步骤 S5：兜底恢复（可选）**  
语义映射未命中或存在歧义时，可触发查询类工具（如获取已安装应用列表），将结果返回模型并可选刷新词典，模型纠正后重试业务工具。热路径仍为一次业务调用；仅失败时进入查询恢复路径。

### 2.4 统一引用协议（两类引用，同一管道）

**（1）结果引用——承接本会话工具返回**

- 形式：`${<resultId>.<字段路径>}`  
- 约定：`resultId` 仅字母数字且不含点号，用首个 `.` 分隔字段路径；字段路径支持点号嵌套。  
- 数据源：工作记忆中的工具结果；查找顺序建议为「全量工具返回集合优先，再查工具适配视图」。  
- 示例：`${a1b2c3d4.fileUri}`

**（2）语义实体引用——承接稳定业务对象标识**

- 形式（三段式）：`${<命名空间>.<实体>.<属性>}`  
- 命名空间可扩展，例如应用 `app`、联系人、设备等。  
- 模型只表达「哪个实体的哪个属性」，例如 `${app.抖音.bundleName}`。  
- 数据源：语义词典（见 2.5）。

**判别：** 去掉 `${}` 后，若首段为已注册命名空间则走语义求值，否则按结果引用（或短句柄映射）处理。

### 2.5 语义词典：同义词表 + 映射表

| 表 | 作用 | 示例 |
|----|------|------|
| 同义词 / 别名表 | 将 douyin、Douyin、抖音等归一为规范实体名 | douyin → 抖音 |
| 实体属性映射表 | 规范实体 + 属性 → 真实标识 | (app, 抖音, bundleName) → com.ss.android.ugc.aweme |

求值：先别名归一，再查映射；0 条失败，1 条成功，多条歧义失败并返回候选。词典可由预置数据与设备查询结果刷新共同维护。

### 2.6 与提示 / 技能约定的配合（非唯一手段）

通过技能或系统提示约定：对 bundleName 等参数直接填语义引用；对上游结果字段填结果引用或原样复制上下文中已出现的占位符；用户原话或可独立确定的短字面量仍可直接填写。  
**硬约束在拦截器求值与短路**；提示仅为辅助，保证工具零改动下同类参数自动覆盖。

### 2.7 实施例：应用权限工具（包名场景）

用户意图：禁止抖音使用麦克风。  

- **原路径：** 先调获取已安装应用列表 → 模型从列表抄包名 → 再调禁止权限工具（两次循环；仍可能抄错或编造）。  
- **本方案路径：** 模型直接调用  
  `forbidPermission(bundleName="${app.抖音.bundleName}", permission="麦克风")`  
  拦截器查同义词与映射表得到真实包名后执行；**正常路径一次循环**；工具实现无改动。

### 2.8 实施例：跨工具文件地址传递

工具 A 返回长文件地址并写入工作记忆；送模时可掩码为 `${resultId.fileUri}`；工具 B 入参原样使用该占位符；拦截器从工作记忆展开真值后执行。

### 2.9 实施例：引用展开后的入参策略化格式转换

工具 A 返回标识列表（如 `merged_id_list`）并写入工作记忆。模型调用工具 B 时，将 `images` 参数填写为 `${resultId.merged_id_list}`，不生成下游所需的对象数组。调度层首先将引用展开为真实列表；随后根据该参数配置的转换策略，将列表中每个元素映射为包含 `file_id` 字段（值为元素的字符串形式）的对象，得到例如 `[{"file_id":"563"}, …]` 后再调用工具 B。从而在工具零改动前提下，完成“跨工具传值 + 结构适配”，避免模型改写长结构化入参。

## 三、保护点

再次强调保护的是**技术方案实现**，而非需求或效果口号。

### 保护点 1（核心方案）

一种面向智能体工具链的参数引用解析方法：大模型在工具调用参数中输出统一引用占位符；工具调度框架在工具执行前通过统一拦截器扫描并解析占位符，从工作记忆和/或语义词典查表得到真实参数值并回填后再执行工具；解析失败则短路且不将占位符字面量传递给工具；工具侧接口与实现无需为引用能力进行改造。

### 保护点 2（双数据源引用协议）

所述占位符至少支持：  
（a）基于会话工作记忆的结果引用 `${结果标识.字段路径}`；  
（b）基于可扩展命名空间的语义实体引用 `${命名空间.实体.属性}`；  
二者经同一拦截器求值管道处理，并按首段是否为注册命名空间等方式进行类型判别。

### 保护点 3（语义消歧结构）

语义实体引用通过「同义词/别名归一表 + 实体属性映射表」两级查表得到真实标识（如应用包名），使模型仅输出应用名等语义表达，真实标识不由模型生成。

### 保护点 4（掩码与所见即所填）

对选定工具结果字段，在送入大模型前替换为引用占位符；模型将上下文中出现的占位符作为后续工具参数值原样输出，由拦截器展开，从而避免模型抄写长真值。

### 保护点 5（架构组成关系）

系统包括：大模型交互模块、带引用解析拦截器的工具调度模块、工作记忆模块、语义词典模块、工具执行模块；拦截器串接于调度模块与执行模块之间，对所有工具调用参数生效以实现全覆盖。

## 四、有益效果

1. **针对多轮查询开销：** 通过语义实体引用 + 词典求值，使应用包名等场景在映射命中时**一次工具循环**即可完成业务调用，无需先查全量列表再调用。  
2. **针对标识幻觉：** 真实包名 / 文件地址等来自映射表或工作记忆，模型不承担“生成真实标识”的职责，**结构性降低幻觉**。  
3. **针对长值照抄错误与上下文膨胀：** 结果引用与送模掩码减少长字符串复述，降低截断/改写概率，并节约 Input Token、改善时延。  
4. **针对工具改造成本：** 解析发生在框架统一入口，**工具零改动**即可覆盖全部携带同类参数的工具。  
5. **可恢复性：** 映射失败或歧义时短路并支持查询兜底刷新后重试，避免错误字面量进入工具造成误操作。

取证对象为**友商已上市/可获取的产品或服务行为**，证明其实现落入保护点对应的技术特征组合。注意：效果表象（如变快、少一轮）只能作怀疑线索，不能单独作为最终证明。

| 保护点对应特征 | 建议取证手段（黑盒 / 旁路可观测） |
|----------------|----------------------------------|
| 模型侧输出占位符、执行侧才出现真值 | 在可拦截的工具调用通道（代理、抓包、调试桥、开放 API 日志等）对比：模型可见的 tool arguments 含 `${…}` 或等价引用态，而实际打到业务工具/系统接口的请求已是真实包名或 URI。 |
| 统一拦截、工具未逐个改造 | 对多个不同工具（凡带 bundleName/fileUri 等参数）重复上述对比，若均呈现“入参引用态 → 执行前变真值”的同一行为模式，可佐证框架层统一处理而非单工具定制。 |
| 语义三段式 + 同义词归一 | 分别使用「抖音」「douyin」等不同别名触发同一操作，若最终落到同一真实包名，且首轮未调用“枚举已安装应用”仍能成功，可佐证存在别名归一与映射求值。 |
| 工作记忆结果引用 | 构造“上一工具返回长标识 → 下一工具参数为短引用态”的对话，观测下一工具实际请求携带与上一工具返回一致的真值，而模型参数未出现完整真值抄写。 |
| 解析失败短路 | 故意使用不存在的引用；若工具侧未收到含 `${` 的非法包名/地址，且产品返回引用解析类错误或自动走查询纠正流程，可佐证“失败不透传”。 |
| 与纯提示约束的区分 | 在关闭网络词典/清空映射的条件下，仅靠提示无法稳定得到正确包名；恢复映射后恢复稳定——用于区分“仅靠 Prompt”与“查表求值机制”（需在实验条件可控制时使用）。 |

**不推荐作为充分取证：** 仅比较时延或轮次减少；仅主观体验“不容易幻觉”；无法证明具体技术特征时推测友商内部代码（通常不可获取）。

#### 相近文献 2：公开技术——模型不可见的机密/凭证引用注入（如动态密钥引用在执行包装层解析）

- **相近点：** 均存在“引用态字符串在执行前被解析为真值、且真值尽量不回灌模型”的思路。  
- **与本发明在保护点上的区别：**  
  1. 现有公开多针对**密钥/凭证**，常将敏感参数从模型可见工具 schema 中剥离或禁止模型填写，由运行时注入；本发明针对**业务工具参数**（包名、文件 URI、上游结果字段等），模型仍填写参数位，但填写的是**业务引用意图**。  
  2. 本发明包含面向会话工具结果的 `${结果标识.字段路径}` 协议、送模掩码，以及面向应用等对象的 `${命名空间.实体.属性}` + 双表归一映射，用于消歧与降幻觉，并非密钥保险库路径解析。  
  3. 本发明明确以**减少查询轮次、消除业务标识幻觉、工具无改造覆盖**为组合技术路径，与机密治理目标不同。

#### （可选补充）工作流剧本中的状态变量替换类公开

- 若检索到智能体剧本/全局状态中 `${state.xxx}` 由编排引擎替换的方案：其变量通常由**编排作者预置**，不是模型在多工具 Function Call 实参中按统一协议引用「上一次工具结果」或「语义实体属性」，且一般不解决包名幻觉与工具零改动的组合问题。区别仍落在保护点 1～3 的协议与拦截位置上。

### 6.3 新颖性 / 创造性初步判断（内部）

在已见表述中，将下列特征组合作为创造性论述重点：

**统一工具入参引用协议（结果引用 ∪ 语义三段式）+ 执行前统一拦截求值 + 双表语义消歧 + 失败不透传 + 工具无感全覆盖（可选叠加送模掩码）。**

单点“变量替换”或“密钥引用”不足以覆盖上述组合；正式结论以检索报告为准。

## 八、摘要（可直接用于 IDEA / 说明书摘要栏）

本发明公开一种面向智能体工具链的参数引用解析机制。大模型在工具入参中输出统一引用占位符，而不直接生成易幻觉或易抄错的真实标识；工具调度框架在执行前通过统一拦截器解析占位符，分别从会话工作记忆（结果引用）和语义词典（命名空间.实体.属性，经同义词归一与属性映射）查表回填真值后再调用工具，解析失败则短路且不透传字面量。从而在工具零改动前提下，降低多轮查询与长值照抄成本，结构性抑制包名等弱语义标识的幻觉，并适用于跨工具传参与端侧应用操控等场景。
