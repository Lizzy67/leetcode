# visionContext 到底是什么

> 用大白话对齐：结构怎么定、和搜索结果、对话历史、模型上下文各是什么关系。  
> 上一版字段太多，容易看成「每张图一个大对象 + 再套一层 visionContext」。这篇以这份为准。  
> 业界对照见 [`vision-context-industry-practice.md`](./vision-context-industry-practice.md)。

## 两个容易看混的词

**`m12` 不是现有字段，也不是你提过的名字。** 它只是举例：Runtime 把一张图写入账本时，可以自己发一个会话内短号，让模型写 `${vision.m12}`，而不去抄图库 id 或一长串 url。不用这个名字也行。序号已经够用时，模型直接写 `${vision.lastSearch[2]}`，账本里可以不出现 `m12`。

**`listPath` 是旧工具的适配，不是新工具的返回规范。**

- 新工具：按约定的字段返回，例如每张图放在 `media[]`，里面有 `ref` 和 `from`。Runtime 认这个固定字段，直接入账。
- 旧工具：图库搜索已经返回 `items[].galleryId`，不能改成 `media[]`。接入方在工具策略里写 `listPath: items`、`refPath: galleryId`，告诉 Runtime「图片在你原来的这个字段」。Runtime 照这个路径去取，再写入同一本账本。

## 先回答 7 个问题

### 1. 要不要兼容所有会返回图片的工具？

**不要改这些工具的返回格式。**

图库搜索继续返回它现在的 id 列表，文生图继续返回它的 url，上传继续是 obs。各写各的。

要统一的只有 Runtime 记笔记的方式：工具一返回图，Runtime 从这份返回里**抽出一行小记录**放进本会话的图片账本。工具本身不用改成同一种 JSON。

### 2. mediaItem 是不是每张图存一个很大的结构？

**不是。** 上一版把宽高、标签、caption、签名、过期时间都写进一条记录，那是「以后可能用到的字段清单」，不是落库形态。

一张图只留定位它所需的几项：

```json
{
  "id": "m12",
  "from": "gallery",
  "ref": "10082",
  "batch": "a1b2c3d4",
  "index": 2
}
```

| 字段 | 含义 |
|------|------|
| `id` | 本会话里这张图的短号，后面指代用 |
| `from` | 从哪来：`gallery` 图库 / `upload` 上传 / `web` 网图 / `gen` 文生图 / `edit` 修图结果 |
| `ref` | **一个**能找到原图的值：图库 id，或沙箱 uri，或公网 url，或 obs id。不把四种都存满 |
| `batch` | 哪一次工具返回的。值就是现有 workmemory 的 `resultId` |
| `index` | 这一批里的第几张（从 0 起）。「第 3 张」用它 |

像素不存。搜索接口已经返回的缩略图、时间、摘要也不再复制一份。

### 3. 搜索那边是不是已经做了？mediaItem 和对话历史是不是同一层？

搜索结果**已经在** workmemory 的 `resultDataList` 里，这是对的，继续用。

所以 mediaItem **不是**对话历史里的一条消息，也**不是**把搜索 JSON 再抄一遍。

同一场会话里其实有三层，别叠在一起：

```text
对话历史          用户说的话、模型说的话、工具返回的摘要
                  「搜索去年拍的照片」这句话就在这里

workmemory        每次工具的完整返回（搜索的 id 列表在这）
                  已有，不用重做

图片账本          只给「图」建的索引：短号 + 指向 workmemory 或上传文件
visionContext     默认不写进对话历史
```

搜索到的图：`batch + index` 指回那次搜索结果即可，`ref` 用图库 id。  
上传、文生图、只出现在回复 Markdown 里的图：搜索结果里没有，才靠账本自己记下 `ref`。

### 4. 在模型上下文里大概在什么位置？

**整本账本不放进模型上下文。**

模型看到的仍是现在这种对话：

```text
user:     搜索去年拍的照片
tool:     找到 48 张。引用 ${a1b2c3d4}
          （可选）前 30 张缩略图
assistant: 找到 48 张，要第几张？
user:     第 3 张拿去修图
```

48 张的 id 列表留在 workmemory / 账本。模型只拿到摘要、短引用，以及产品决定给它看的那最多 30 张。  
「第 35 张」模型没看见图也没关系，它只要说出「第 35 张」，Runtime 用 `index` 去账本里取。

### 5. 已经有全量 mediaItem，为什么还要 visionContext？

**它们是同一个东西，不是两层。**

- `mediaItem` = 账本里的一行（一张图）
- `visionContext` = 这场会话的那本账本（很多行 + 三个指针）

没有「先存完全量 mediaItem，再包一个 visionContext」这步。叫 visionContext，只是给这本账本一个名字，方便和对话历史、workmemory 分开说。

三个指针才是账本比「一堆 mediaItem」多出来的东西：

```json
{
  "items": [ /* 上面那种小记录 */ ],
  "lastSearch": "a1b2c3d4",
  "lastUpload": ["m3"],
  "picked": ["m12"]
}
```

| 指针 | 干什么 |
|------|--------|
| `lastSearch` | 「搜索结果里的第 x 张」指哪一次搜索。后面又文生图了，也不会把这次搜索冲掉 |
| `lastUpload` | 「我刚传的那张」 |
| `picked` | 用户已经选中的图。「有太阳的那张」「就这张修」写在这里，下一句修图直接用 |

`lastToolReturnImg` 可以不单做一份数据：最近一次工具如果是搜索，它就是 `lastSearch`；如果是修图，新图已经在 `items` 里，并把 `picked` 改成这张新图。

### 6. visionContext 什么时候生效？

没有单独的开关。两件事：

**写入**（有图进来就记一行）：

- 图库搜索返回
- 用户上传完成
- 文生图 / 网搜吐出图
- 修图、剪辑做出新图

**读出**（下一轮要拿图给工具时）：

用户说「第 3 张拿去修」或「有太阳的那张拿去剪」。模型参数里写引用，例如 `${vision.lastSearch[2]}` 或 `${vision.picked}`。工具真正执行前，Runtime 查账本，换成图库 id / obs / url，再调用修图或剪辑。

不修图的纯聊天轮次不用读它。

### 7. 和对话历史重复吗？里面还有搜索 query

**query 不该出现在账本里。** 上一版写了 `lastSearchBatch.query`，和用户原话重复，删掉。

对话历史负责「用户说过什么」。  
账本只负责「哪张图、在哪、第几张、当前选中谁」。

### 8. Runtime 怎么知道这次返回里有图？

**不靠扫返回 JSON 猜。** 工具在接入时声明「我的结果里图片在哪」。没声明的工具，返回里即使有 url，Runtime 也不入账。

声明写在工具配置上（和现有 mask policy 放一起），例如：

```json
{
  "gallery.search": {
    "media": { "listPath": "items", "refPath": "galleryId", "from": "gallery" }
  },
  "image.generate": {
    "media": { "listPath": "images", "refPath": "url", "from": "gen" }
  }
}
```

这次调用成功返回后，Runtime 只做一件机械的事：这个工具有没有 `media` 配置。有，就按 `listPath` 取出数组，每一项用 `refPath` 拿出那个 id 或 url，追加一行，`batch` 用这次的 `resultId`。没有，就跳过。

搜索、文生图、网搜走的是**同一段入账代码**。差别只在各自那三行配置。Runtime 里不要写 `如果是搜索工具就入账`。新工具要入账，给它补一份 `media` 配置即可，不用改 Runtime。

补配置的人是这个工具的接入方，和现在补 mask、`beforeHookPolicy` 是同一份工具策略、同一次发布。不改工具返回 JSON，不改 Runtime 代码，也不写进 Skill 正文。

举例：新工具 `web.imageSearch` 自己返回的是：

```json
{
  "summary": "找到 12 张剧照",
  "photos": [
    { "src": "https://img.example/1.jpg", "title": "封面" },
    { "src": "https://img.example/2.jpg", "title": "侧脸" }
  ]
}
```

接入方在该工具已有策略旁加上这三项，字段名对上它自己的 JSON：

```json
{
  "web.imageSearch": {
    "media": {
      "listPath": "photos",
      "refPath": "src",
      "from": "web"
    }
  }
}
```

| 填什么 | 怎么填 |
|--------|--------|
| `listPath` | 图片数组在返回 JSON 的哪一层。上面是 `photos`。搜索若是 `items`，就写 `items` |
| `refPath` | 数组里每一项，用哪个字段当这张图的 id 或 url。上面是 `src`。图库是 `galleryId` |
| `from` | 来源枚举里选一个：`gallery` / `upload` / `web` / `gen` / `edit` |

只返回一张、没有数组时，`listPath` 留空，`refPath` 写那个字段名，例如文生图的 `imageUrl`。

发布后，这个工具下一次成功返回，已有的入账代码读到 `media`，就按 `photos[].src` 各写一行。没写这三项的工具，结果仍进 workmemory，但不进 visionContext。

上传不是工具返回。客户端上传完成时发一条「上传完成」事件，事件里带 obs id，走同一条追加逻辑，`from` 固定为 `upload`。

### 9. 「第 3 张」「有太阳的那张」是谁写入 picked 的？

**落笔的始终是 Runtime。决定选哪张的不是 Runtime。**

| 用户说的 | 谁决定是哪张 | Runtime 做什么 |
|----------|--------------|----------------|
| 第 3 张 | 模型。它在修图参数里写 `${vision.lastSearch[2]}`，只写序号，不写图库 id | 用 `lastSearch` 这批的 `index = 2` 找到那一行，把这行的 `id` 写入 `picked`，再拿 `ref` 去调修图 |
| 有太阳的那张，且这张在给模型看的图里 | 模型。给它的缩略图旁边带有 `m12` 这种短号，它在参数里写 `${vision.m12}` | 把 `m12` 写入 `picked` |
| 有太阳的那张，且不在那 30 张里 | 选图工具。模型先调选图，入参是这批的 batch 和「有太阳」；选图工具返回它看中的 `id` | 选图工具已声明自己返回的是选中 id，Runtime 按这个声明把返回的 id 写入 `picked` |

用户那句话本身不写 `picked`。模型没点名、选图工具也没返回 id 时，`picked` 保持原样，修图调用失败并让模型再选，不猜。

「第 3 张」时，模型**不翻** visionContext。整本账本不在它的上下文里。它只从用户那句话里听到「第三张」，在修图参数里写序号 `${vision.lastSearch[2]}`。Runtime 拿这个序号去账本里取。

### 10. 选图工具是谁的？要内置吗？有几种选法？

**做成 Runtime 内置工具 `vision.select`，不让每个业务自己做一份。** 它要读整本账本（含模型没看见的那部分），还要把选中的 id 交回 Runtime 写 `picked`。普通业务工具做不到这件事。

它只回答「是哪几张」，返回账本里已有的短号。不下载、不上传、不改格式、不把图库 id 换成云地址。那些发生在后面真正调用修图或剪辑时，由 Runtime 按下一个工具的 `runsOn` 只搬 `picked`。

真正「看图」可以交给已有能力，但对外只有这一个工具。选法就四种，够用了：

| 选法 | 用户怎么说 | 要不要调 `vision.select` | 怎么选 |
|------|------------|--------------------------|--------|
| 序号 | 第 3 张、最后两张 | 不调 | 模型写序号，Runtime 按 `index` 取 |
| 模型眼前这张 | 有太阳的那张，且在给它看的几十张里 | 不调 | 模型按缩略图旁的短号写 `${vision.m12}` |
| 看整批才知道 | 有太阳的那张，不在那几十张里 | 调 | 先用图库已有标签滤；没有标签，再把这批缩略图交给视觉模型，返回短号 |
| 用户自己点 | 界面上勾了几张 | 不调模型 | 客户端把点中的短号直接交给 Runtime 写 `picked` |

不把「按颜色、按人脸、按文字」各做一个工具。那些都是第 3 种里的描述词，由这一次视觉模型或图库标签处理。

### 11. 端剪辑要下载、云修图要上传吗？

**要。只搬 `picked` 里那几张，由 Runtime 在调用前搬，不由修图或剪辑工具自己搬。**

工具配置里再声明它在哪一侧跑、认哪种地址：

```json
{
  "video.clip": { "runsOn": "device", "accepts": ["gallery", "sandbox"] },
  "image.edit": { "runsOn": "cloud", "accepts": ["obs", "http"] }
}
```

调用前 Runtime 对照 `picked` 那一行的 `from`：

| 图在哪 | 下一个工具在哪 | Runtime 做什么 |
|--------|----------------|----------------|
| 图库 / 沙箱 | 端上剪辑 | 地址直接给，不上传 |
| 公网 url / obs | 端上剪辑 | 下载到沙箱，把沙箱地址给剪辑工具 |
| obs / 公网 url | 云上修图 | 地址直接给，不重复上传 |
| 图库 / 沙箱 | 云上修图 | 上传到 obs（或换成云侧能拉的地址），把云地址给修图工具 |

搬完只改这一行当时要用的地址，不把 48 张搜索结果都上传或下载。上传或下载失败就停，不把端上图库 id 丢给云工具。

## 和你说的场景怎么对上

用户：搜索去年拍的照片。

1. 图库搜索照旧返回，完整 id 列表进 workmemory（搜索侧已有的那份）。
2. Runtime 按张追加小记录，`batch` 都是这次的 `resultId`，`index` 为 0, 1, 2…
3. `lastSearch` 指到这次。
4. 模型上下文只看到「找到 48 张」+ 引用 + 最多 30 张缩略图。

用户：选第 3 张。

5. 模型写 `${vision.lastSearch[2]}`。Runtime 用这个序号找到行，把该行 `id` 写入 `picked`。

用户：搜索结果里有太阳的那张。

6. 在给模型看的图里：模型写 `${vision.m12}`。Runtime 把 `m12` 写入 `picked`。
7. 不在这 30 张里：模型先调选图工具。选图工具返回 `id` 后，Runtime 按该工具的声明写入 `picked`。

用户：拿去修图 / 剪视频。

8. 模型只传 `${vision.picked}`。
9. 执行前 Runtime 只搬 `picked` 里那几张：云修图遇到图库 id 就先上传，端剪辑遇到公网图就先下载到沙箱。

修完的图再追加一行（`from: "edit"`），`picked` 改成新图。下一句「再淡一点」或「放进剪辑」还是用 `picked`。

## 不要做的事

- 不要求所有返回图片的工具改成同一种大 JSON。
- 不把每张图的宽高、标签、query、过期时间都存上。
- 不把账本整本塞进模型上下文。
- 不把搜索结果在 workmemory 和账本各存一份全文。搜索只在账本留 `batch + index + 图库 id`。
- 不在账本里再存用户的搜索 query。
- 不靠扫描返回 JSON 猜测「这里有没有图」。只有声明了 `media` 的工具，以及上传完成事件，才会入账。
- 不让 Runtime 自己理解「第 3 张」或「有太阳」。序号和短号由模型或选图工具给出，Runtime 只负责把给出的结果写入 `picked`。
- 不把选图拆成多个业务工具。序号和「眼前这张」不用选图工具；看整批才用内置 `vision.select`。
- 不在 Runtime 里为搜索单独写一段入账。入账代码只有一份，搜索只是多了一份 `media` 配置。
- 不让选图工具做格式适配。它只返回短号。上传、下载发生在下一个业务工具调用前。
- 不把整批搜索结果上传或下载。只在调用前搬 `picked`，端云各认各的地址。
